# 시나리오별 동시성 제어 도입방식

## 1. 예약
- 여러 사용자가 하나의 리소스를 경합하여 한 명만 성공해야 함.
  - **예시**: 예약1과 예약2가 동시에 진행될 때,
    - 예약1: 성공
    - 예약2: 실패
- 실패한 사용자는 이미 예약되었다는 메시지를 받아야 함.
- **비관적 락**: 어차피 실패할 사용자들이 대기 시간만 발생.
- **낙관적 락**: 대기가 없지만 롤백에 대한 부담이 있음.
- **Redisson 분산 락**: 문제없이 사용가능
- **결론**: Redisson 분산 락 + 낙관적 락 (보험으로).
  - **성능 테스트**: 세 가지 방법 모두 구현 후 성능 분석

---

## 2. 충전
- 정책에 따라 다르게 처리될 수 있음.
- **동시 충전은 오류로 보고 허용하지 않기로 정책 설정** (중복 클릭 또는 빠른 연속 클릭).
  - **예시**: 충전1과 충전2가 동시에 진행될 때,
    - 충전1: 성공
    - 충전2: 실패
- 자원이 한 명의 사용자 데이터이므로 충돌이 적을 것으로 예상.
- **비관적 락**: 하나만 성공해야 하기 때문에 적합하지 않음.
- **낙관적 락**: 충돌이 적은 환경에서 효율적으로 사용 가능.
- **Redisson 분산 락**: DB 부하를 줄일 수 있어 좋음.
- **결론**: Redisson 분산 락 사용.
  - 낙관적 락도 가능하지만, 아래 4번 **충전+사용** 케이스로 인해 사용하지 않음.

---

## 3. 사용
- 정책에 따라 다르게 처리될 수 있음.
- **동시 사용은 오류로 보지 않고 허용하기로 정책 설정** (매크로로 여러 좌석 동시 결제 허용).
  - **예시**: 사용1과 사용2가 동시에 진행될 때,
    - 사용1: 성공
    - 사용2: 성공
- **비관적 락**: 결제와 관련된 중요한 내용이므로 무결성 보장이 필요.
- **낙관적 락**: 모든 동시성이 실행되어야 하므로 적합하지 않음.
- **Redisson 분산 락**: DB 부하를 줄일 수 있어 좋음.
- **결론**: Redisson 분산 락 사용.
  - 비관적 락도 가능하지만, 아래 4번 **충전+사용** 케이스로 인해 사용하지 않음.

---

## 4. 충전+사용
- 충전과 사용이 동시에 발생하는 것은 오류가 아니기 때문에 모두 성공해야 함.
  - **예시**: 충전1과 사용1이 동시에 진행될 때,
    - 충전1: 성공
    - 사용1: 성공
- DB 락을 사용할 때,
  - 충전은 낙관적 락을,
  - 사용은 비관적 락을 사용해야 함 (이 둘은 일치하지 않음).
- **결론**: 두 케이스 모두 공통으로 사용 가능한 **Redisson 분산 락** 사용.
