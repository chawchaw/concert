# 포인트 충전 시 낙관적 락과 레디슨 분산 락의 차이

## 정책 및 요구 사항
- 동시에 요청되는 충전은 하나만 성공해야 합니다.

## 낙관적 락 사용 시 문제점
- **성공률 문제**: 동시에 요청이 들어오지만, 테스트 시 100개 중 약 12개만 성공합니다. 여러 번 시도해도 성공 수가 일정하게 12개로 유지됩니다.
- **로그 분석**: 성공하는 주기가 거의 일치하며, 100개 동시 요청 시 12개가 성공한 기록이 있습니다.

  ![image.png](https://prod-files-secure.s3.us-west-2.amazonaws.com/c44830da-559a-41d1-a474-1e2195c139af/abf4e233-af3e-441c-999a-7bde1cc98f2c/image.png)

- **MySQL 커넥션 풀 의존성**: 실패가 주기적으로 나타나 커넥션 풀을 확인해보니 기본값이 10개로 설정되어 있었습니다.
    - 커넥션 풀을 20개로 증가 후 동시 요청을 20개로 제한하니 성공했습니다. (기본값 10개에서 동시 요청 20개일 때는 2개 성공)
    - **결론**: 낙관적 락은 커넥션 풀 크기 부족이 동시 요청 실패율이 올라갈 수 있습니다.

## 레디슨 분산 락을 통한 해결
- **레디슨 분산 락 설정**: 모든 요청을 실패시키고 하나만 성공시키기 위해 대기 시간을 0초로 설정했습니다.
- **테스트 결과**:
    - 커넥션 풀 기본값(64개)으로 1000개의 요청을 테스트한 결과, 하나만 성공했습니다.
    - 5000개의 요청에서는 29개가 성공했으나, 한 사용자가 동시에 5000번 요청하는 경우는 비현실적이므로(경찰에 신고해야할 것 같습니다, 디도스 공격으로 간주하고 막아야할 것 같습니다), 1000개 요청에서도 충분한 성능이라고 판단됩니다.

## 결론
- **낙관적 락의 한계**: 현실 환경에서는 이미 커넥션 풀을 많이 사용하고 있기 때문에 낙관적 락의 성공률이 낮아지며, 환경에 따라 성공 여부가 크게 달라질 수 있습니다.
- **레디슨 락의 효율성**: 레디슨 락은 대기 시간을 0초로 설정해 커넥션 리소스가 적어도 많은 동시성 요청을 제어할 수 있습니다.
    - 동시성 제어 방식의 차이:
        - **낙관적 락**: 트랜잭션을 먼저 실행하고 커밋 시 버전을 체크하기 때문에 시간차가 발생
        - **레디슨 분산 락**: 시작 시부터 락을 체크하여 낙관적 락보다 처리 속도에 유리
- **결론**: 레디슨 분산 락이 성능적으로 동시성 제어에 유리하고, RDB 부하를 줄이는 데 적합하다고 판단됩니다.

## 추가 의문점
- **비관적 락의 대기시간 0초 사용**: 비관적 락에서 대기시간을 0초로 설정한다고 해서 레디슨 락과 동일한 방식이 되는 것은 아니지만, 레디슨 락과 유사하게 사용할 수 있는 방법은 어떨지 궁금합니다.
