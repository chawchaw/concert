# 부하테스트 분석 및 성능 개선 방안

## 결과 요약
- 결과: [부하테스트.md](./부하테스트.md) 참고
- RPS: 250
- 분석지표: p95 응답속도
- Redis
  - CPU
    - 1 core > 2 core: 0.7초 개선(110% 향상)
    - 2 core > 4 core: 개선없음
  - RAM
    - 0.5G > 1G: 3.4초 개선(150% 향상)
    - 1G > 2G: 0.3초 개선(120% 향상)
    - 2G > 4G: 개선없음
- MySQL
  - CPU
    - 1 core > 2 core: 개선없음
  - RAM
    - 1G > 2G: 개선없음
- Application
  - CPU
    - 1 core > 2 core: 20.1초 개선(330% 향상)
    - 2 core > 4 core: 5.4초 개선(240% 향상)
    - 4 core > 6 core: 1.5초 개선(170% 향상)
    - 6 core > 8 core: 0.7초 개선(140% 향상)
  - RAM
    - 1G > 2G: 개선없음

## 컨테이너별 분석
- Redis
    - CPU 는 1 core 이상 의미가 없음
    - RAM 은 2G 이상 이상 의미가 없음
- MySQL
    - CPU 는 1 core 이상 의미가 없음
    - RAM 은 2G 이상 이상 의미가 없음
- Application
    - CPU 는 core 가 많아질수록 성능이 향상됨
    - RAM 은 1G 이상 의미가 없음

## 주인공은 Application CPU!
- Application CPU 성능을 향상시키는 것이 가장 중요함
- 특히 6코어가 넘어가면서부터 목표지수인 p95 3000ms 미만을 달성함
- 나머지 성능은 최소한의 리소스만 할당해도 충분함

## 최종 적정 스펙
- Redis
    - CPU: 2 core
    - RAM: 2G
- MySQL
    - CPU: 1 core
    - RAM: 1G
- Application
    - CPU: 8 core
    - RAM: 1G

## 왜 Application CPU가 중요할까?
- 대기열 로직 분석
  - 회원가입
    - 입력 데이터 검증
      - 아이디, 비밀번호 길이 등
      - CPU 바운드: 낮음(단순 계산, 문자열 처리)
    - 비밀번호 해싱
      - CPU 바운드: 높음(복잡한 계산)
    - 데이터베이스 저장
      - 사용자 정보를 DB에 저장
      - I/O 바운드: 높음
    - 결론: I/O 바운드 높음(비밀번호 해싱이 CPU를 많이 사용하지만, 대부분의 시간은 DB 저장에서 소비)
  - 로그인
    - 입력 데이터 검증
      - 아이디, 비밀번호 길이 등
      - CPU 바운드: 낮음(단순 계산, 문자열 처리)
    - 비밀번호 해싱
      - CPU 바운드: 높음(복잡한 계산)
    - 데이터베이스 조회
      - 사용자 정보를 DB에서 조회
      - I/O 바운드: 높음
    - 결론: I/O 바운드 높음(비밀번호 해싱이 CPU를 많이 사용하지만, 대부분의 시간은 DB 저장에서 소비)
  - 대기열 입장/조회
    - Redis 조회
      - 사용자 ID를 Redis에서 조회
      - I/O 바운드: 높음
    - Redis 저장
      - 사용자 ID를 Redis에 저장
      - I/O 바운드: 높음
    - 결론: I/O 바운드 높음
- 분석결과
  - 주로 I/O 바운드가 많음
  - 쓰레드 풀이 부족해지는 순간부터 컨텍스트 스위칭이 발생하여 성능이 떨어짐

## 이대로 끝내기엔 찝찝하니 시각화 해보자
- JVM Micrometer 를 사용하여 쓰레드 관련 성능 지표를 수집해보자
  - CPU: 사용량, Context Switching Rage
  - 쓰레드: 활성 수, 총 쓰레드 수, 블로킹된 쓰레드 수, 대기중인 쓰레드 수
  - I/O: 대기시간
  - 메모리: GC 중단 시간
