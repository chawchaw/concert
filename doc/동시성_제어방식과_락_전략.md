# 가능한 동시성 제어 방식들의 장단점

## 비관적 락
- **충돌이 발생한다고 비관적으로 가정**

### 장점
- 데이터 무결성이 보장됨
- 구현이 간단함 (충돌 발생 시 처리가 쉬움)

### 단점
- 대기 쓰레드가 많아짐
- 무분별한 사용 시 데드락이 발생할 수 있음

### 특징
- **성능**: 충돌이 많으면 대기 시간이 길어져 성능 저하가 됨
- **구현 복잡도**: 데드락을 방지하기 위해 복잡해질 수 있음
- **효율성**: 락이 걸리면 자원이 비효율적으로 사용됨

### 결론
- 충돌이 자주 일어나지만 적은 수의 충돌을 간단히 해결할 때 유용

---

## 낙관적 락
- **충돌이 발생하지 않는다고 낙관적으로 가정**

### 장점
- 대기가 잠깐만 걸림 (비관적 락에 비해)
- 데드락이 발생하지 않음

### 단점
- 충돌이 생기면 롤백이 발생됨
- 구현이 복잡함 (충돌 발생 시 재시도를 몇 번까지 할 것인지?)

### 특징
- **성능**: 충돌이 적은 경우 대기가 없으므로 자원 활용이 좋아짐
- **구현 복잡도**: 버전 관리와 충돌 발생 시 재시도 또는 처리 로직이 필요함
- **효율성**: 충돌이 적다면 매우 효율적이지만 많다면 비효율적 (롤백 처리 비용)

### 결론
- 충돌이 드문 경우 효율적으로 사용할 수 있어서 유용

---

## 비관적 락 & 낙관적 락의 공통 단점
- 락을 걸 자원이 존재해야만 사용 가능
- 현실적으로 DB 부하를 줄이기 위해 지양될 수 있음
    - 인스턴스는 스케일 아웃이 가능하지만, master DB는 스케일 아웃이 불가능함
    - master DB의 스케일 업을 하더라도 커넥션 수에 한계가 있음

---

## 레디슨 분산 락
- **분산 시스템에서 여러 인스턴스, 노드 간의 락을 공유하여 사용 가능**

### 장점
- 여러 인스턴스에서 접근 가능
- TTL(자동 만료) 사용으로 데드락 방지 가능

### 단점
- 비용 증가
- Redis 관리 작업 필요
- 네트워크 지연 (Redis와 RDB 둘 다 연결 필요)

### 특징
- **성능**: 인메모리 Redis를 사용하기 때문에 성능이 매우 좋음
- **구현 복잡도**: Redis 관리에 추가 리소스가 필요함
- **효율성**: DB의 부하를 줄여주기 때문에 효율성이 높음

### 결론
- 상황에 맞게 다양한 분산 시스템에서 활용 가능
