# Redis를 이용한 대기열 구현

## 대기열이란
- 콘서트 예약을 진행할때 한번에 많은 사람들이 예약을 하면 서버가 다운될 것을 방지해 예약을 할 수 있는 인원을 제한한다.
- 대기하는 사람들은 순서조회만 가능하다.
- 대기가 통과되어야 모든 기능을 사용할 수 있다.
- 대기열은 선입선출(FIFO) 방식으로 처리된다.

## 기존 방식
- 대기열 토큰을 발급하여 RDB 에 저장한다.
- 대기 순서를 풀링방식으로 조회한다.
- 스케줄러1이 5분마다 30명씩 통과시킨다.
- 스케줄러2가 통과 후 10분이 지난 사용자를 퇴장시킨다.

## 기존 방식의 한계
- 풀링방식은 RDB 에 부하를 많이 준다.
- 아래 시나리오를 예상했을 때 TPS 를 대략적으로 계산해보자.
  - 풀링 TPS
    - 1만명 / 20초마다
    - 10000/20 = 500 TPS
  - 활성 사용자 TPS
    - 평균 10번의 API 호출(콘서트 조회, 일정 조회, 좌석 조회 - 3번, 예약 - 2번, 포인트 조회, 포인트 충전, 결제)
    - 평균 100초 체류
    - 사용자 한명당 10/100 = 0.1 TPS
    - 최대 활성 사용자 60명
    - 60 * 0.1 = 6 TPS
  - 예상 TPS
    - 500 + 6 = 506 TPS
- 대용량 처리를 고려할때 풀링 방식은 RDB 부하가 커지기 때문에 피하는게 좋아 보인다.

## 러프하게 알아보는 AWS instance 가격

  - 32 vCPU, 256 GiB RAM

## 제안
- TPS 가 높은 로직을 Redis 로 대체하는 것이 좋아 보인다.
- 장점
  - RDB 의 부하를 줄여 장애의 위험을 줄일 수 있다.
  - RDB 인스턴스의 스케일을 유지 하고 비용 절감이 가능하다.
  - Redis 는 메모리 기반의 데이터 저장소로 빠른 읽기/쓰기 속도를 제공한다.

## Redis 를 이용한 대기열 구현
- 대기열 입장
  - Sorted Set 사용
  - ZADD (사용자ID) (타임스탬프)
- 순서조회
  - ZRANK (사용자ID)
- 대기열 통과
  - 30명씩
  - ZRANGE 0 30
  - ZREMRANGEBYSCORE waiting_queue 0 [마지막사용자 타임스탬프]
- 활성토큰 발급
  - TTL 사용하여 스케줄러 대체
  - SET (사용자ID) (토큰)
  - EXPIRE (사용자ID) 600
```redis
-- 대기열 입장
ZADD waiting_queue 1620000000 user1
-- 순서조회
ZRANK waiting_queue user1
-- 대기열 통과
ZRANGE waiting_queue 0 30
ZREMRANGEBYSCORE waiting_queue 0 1620000000
-- 활성토큰 발급
SET user1 token1
EXPIRE user1 600
```


# 추가 고민

## 예약 로직
- 사용자가 예약한 후 5분 이내에 결제를 완료해야 한다.
- 5분이 지난 예약은 취소된다.

## 기존 방식
- 스케줄러3이 1분마다 실행된다.
- 예약기한(5분)을 넘은 티켓을 취소시킨다.

## 기존 방식의 한계
- 스케줄러가 매분 0초마다 실행된다.
- 0분 1초에 만료가 되는 티켓은 1분 0초에 취소된다.
- 59초동안 다른 사용자가 예약할 수 없게 된다.
- 이런 케이스가 많아진다면 사용자 경험이 떨어지고 활성사용자가 늘어날 여지가 있다.

## 제안
- Redis의 TTL 을 사용하여 스케줄러3을 대체할 수 있다.
- 스케줄러 의존성을 줄이는 것은 시스템의 안정성을 높일 수 있기 때문이다.
